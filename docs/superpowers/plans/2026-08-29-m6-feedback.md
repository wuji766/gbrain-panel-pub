## 新增建议修（按优先级）

1. **P0：备份活锁 PID 判据穿透 exec 层（条 1 不通过的根因，不修则备份在本机永不可用）**
   - 实测：own 态备份必现 503「检测到活跃锁——疑似外部 serve 已抢占，已中止复制」，`D:\gbrain-backup` 零产物。
   - 根因：面板 spawn 的直接子进程是 `gbrain.exe`（bun shim），它再 exec 出孙进程 `bun …cli.ts serve`——锁文件记录的 pid 是孙进程，`killServe()` 返回的是子进程 pid，`backup.ts` 的 `lockPid === killedPid` 永不成立 → 保守中止。日志佐证：kill→respawn 仅 331ms（≈300ms 等待+判定），无复制动作。
   - 修复方向（任一）：改用 3131 监听归属 PID（netstat）做比对；或认定锁 pid 属被杀进程树（taskkill /T 已杀树，可用 wmic ProcessId/ParentProcessId 链验证）；或 killServe 后按监听端口反查真实 serve pid 再比对。
   - 注：此条是本 backlog「留痕」里"活锁 PID 比对依赖 gbrain 锁 schema（漂移时保守中止）"的真实发作，且在标准 bun-link 安装路径下必现，建议从留痕升级为 P0 必修。

2. **P1：SSE 服务端心跳 / idleTimeout（条 6 部分通过的缺陷 A）**
   - 实测：「连接中断，自动重连中…」并非出现一次，后端恢复后每 ~13s 循环闪现；后端日志出现 `[Bun.serve]: request timed out after 10 seconds. Pass idleTimeout to configure.`
   - 根因：Bun 默认 idleTimeout 10s 杀空闲 SSE，面板 SSE 无心跳（keep-alive comment）——空闲时连接永不稳定，每次 ~3s 重连空窗内到达的事件会丢。
   - 修复方向：SSE 每 ~5s 发 `: ping` 注释行，或 Bun.serve 调大 idleTimeout（心跳更优，兼顾代理场景）。
   - 附带观察（缺陷 B）：后端恢复后 47s 内无自发 MCP 流量，"新事件自动恢复插入列表头部"未获直接证据；修完心跳后建议补一个"重启后事件自动补插"的实测用例。

3. **P2：配置页导航失效（清单外新发现）**
   - 实测：备份页确认弹窗流程之后，点侧栏「配置」无法导航（URL 停在 `#/pages`），Playwright 定位点击与坐标级真实点击均无效；其他路由正常；整页刷新后恢复。复现序列：备份操作 → 页面库 → 配置（不可达）。
   - 疑似 dx 弹窗残留影响路由守卫/事件委托，建议排查（可能与既有"SSE 终态守卫"同源的弹窗生命周期问题）。

4. **口径：retention 0 → 回 5 还是回 1（条 5 后半不符，对应本 backlog 既有条目 6）**
   - 实测：config.json 改 0 重启后配置页显示 **5** 而非 README 验收口径的 1——`config.ts:50` `Number(x) || 5` 把 0 当 falsy 回退默认（仅负数钳到 1）。
   - 既有条目 6"retention 测试细化（toBe(5)/toBe(1) 区分回退与钳制）"正是此分歧；建议 M6 一并定口径：要么改 README（0=用默认 5），要么改实现（0/负数一律钳 1），二选一并让测试口径与文档一致。
