## 二、条7 过程留档（对后续开发有信息量）

备份的 `cpSync` 会**阻塞面板事件循环**：flag 置位后到复制结束期间 `/api/status` 完全无法应答（请求排队），横幅只在复制解除阻塞的瞬间一次性抵达浏览器；备份 flag 实际存在两个对外可见窗口：

- W1：flag 置位（点击 +0.05s）→ cpSync 开始阻塞（约 +0.5~1s）；
- W2：阻塞解除（约 +5~7s）→ POST resolve（约 +8.7s）。

「横幅出现后立刻强杀」因此是窄窗口竞速，共 4 次尝试才命中容忍路径：第 2 击杀晚 6s（浏览器已拿到 false，走快速路径）；第 3 击杀在复制中途（浏览器轮询相位不巧未收到 true，又走快速路径，且留下 1 份 12.8MB 残缺目录）；第 4 击用 watcher 在 W2+0.8s 卡位成功。**结论：任何一条路径都不会无限容忍，逃生口行为正确。**

## 五、给后续开发（M7）的话

1. **优先级建议**：候选池按风险排序——③ key 累积（安全/治理面）＞ ② 残缺备份留存（数据治理，和 rmSync 容错合并成一个「备份目录健壮性」议题）＞ ① 导航静默中止（低频、可自恢复，建议先在 router.onError 里加埋点日志观察）＞ ④ tag 滞留（纯 UI，随手修）。
2. **cpSync 阻塞事件循环**是备份期所有「状态延迟」现象的根因（横幅迟到、status 排队、外部观察者难以判断备份进度）。若 M7 动备份模块，建议把复制改为分片/异步（如按文件分批 + `setImmediate` 让路），或至少在备份期间让 `/api/status` 可应答——这会同时改善 ④ 和逃生口的可观察性。
3. **备份完整性**：目前产物目录名即"完成"语义，无完成标记。强杀/断电后的残缺目录与完整目录无法区分（仅靠体积猜）。建议复制完成后再原子地写一个 `BACKUP_OK` 标记文件，列表与 retention 清理只认标记——残缺目录启动时顺手清理，②即根治。
4. **测试技巧沉淀**（下次验收同类竞速场景可复用）：外部 watcher 轮询 `/api/status` 触发击杀比"浏览器见横幅→模型转发→命令行杀"快且稳；注意 PowerShell 冷启动 1~3s，watcher 要先启动预热再触发场景。
5. README 的 M6 清单条 7 措辞可补一句实际语义：「横幅出现后立刻强杀」在 cpSync 阻塞的现实下等于"kill 落在浏览器已见 true 且未再见 false 的窗口内"，两条离线路径（快速/容忍上限）都算通过——本次验收即按此裁决。
