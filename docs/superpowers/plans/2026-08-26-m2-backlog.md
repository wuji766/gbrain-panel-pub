# M2 待办清单（M1 终审裁决产出）

来源：m1-foundation 分支终审（2026-08-26）。这些是"建议修"级遗留项，合并 M1 后在 M2 开工时消化；"接受现状"项不在此列。

## 首任务（集成缝隙，影响体验）

1. **fallback 后 GbrainClient 端口不跟随**：index.ts 启动时用 `orch.getEffectivePort()` 一次性构造 client，`POST /api/spawn-fallback` 成功切到 3132+ 后，/api/stats 等仍打旧端口 → 401/502，UI 却显示 own@3132。修法：client 改 port getter 或路由内动态取 `orch.getEffectivePort()`。
2. （文档）fallback 仅适用于"3131 被占但锁空闲"；锁被 stdio MCP 持有时 3132+ 上的 serve 也会 LiveServeLockError 秒退——README/代码注释补说明。

## 健壮性（终审 #1/#2/#3/#8）

3. gbrain-client `mcpRequest`：签 key 失败被静默吞（`catch { this.apiKey = null }`），根因被 /mcp 的 401/403 遮蔽。修法：记住签发错误，匿名 /mcp 返回 401/403 时附加进错误消息。
4. Orchestrator 重入守卫：starting/own 态并发 start()、fallback 循环覆盖 `this.proc` → 旧子进程泄漏。
5. killServe 死 PID 守卫：自然退出后 `this.proc` 不置 null，error 态 taskkill 已死 PID（PID 复用窗口）。修法：先查 `exitCode !== null` 走无杀分支。
6. 退出面补强：SIGBREAK 注册 + shutdown once 守卫（防重复信号并发执行）；`server.stop()` 后给在途响应留缓冲。

## 卫生（终审 #12/#14）

7. discovery 每跑累积 2 把永不回收的 key（"gbrain-panel-discover" + 惰性签的 "gbrain-panel"）——M2/M4 做 key 管理时按名复用或 revoke。
8. tsc 遗留 7 处类型错误：orchestrator.ts ×2（pipeLogs 参数类型，生产代码）、gbrain-client.test.ts ×5。

## 接线前置条件（红线，终审 #5 裁决）

9. `clearStaleLock` 在 M1 未接线（只读 /api/stale-lock）。将来接入任何自动清理/按钮前，**必须先补**：空锁目录 10s 宽限期 + rm 前 PID 复核（上游 pglite-lock.ts 有对应防护可参考）。

## 真实链路验证（终审 Important-B）

10. M1 的 29 个测试全跑在 fake-gbrain 替身上；真实 gbrain 的 set-cookie 格式、api-keys 响应字段名（key|api_key|token 三选一假设）、`--surface full` / `--suppress-bootstrap-token` CLI 标志、SSE 行为均未实测。用户执行 README「M1 验收清单」第 5 条 discovery 后，以 `docs/discovery.json` 核对上述假设——发现不符处直接进 M2 计划。
