## 建议修（M7），按风险排序

1. **`gbrain-panel` 自签 key 累积**（安全/治理面，最高优先）：
   验收现场 3 条 active key 同秒（11:24:52）签发，M4 口径预期 1 条——「签发前先撤同名」未完全生效或单次启动多次签发。排查方向：`GbrainClient.issueApiKey` 的 revoke-before-issue 路径与惰性签发竞态（并发首次 mcpCall 同时发现无 key → 各自签发？缓存写入时机？）。
2. **备份目录健壮性**（数据治理；合并既有候选「remove() 的 rmSync 容错」）：
   - 残缺备份留存：强杀面板时失败清理随进程死亡未执行（现场 `gbrain-backup-20260829-040311` 12.8MB 残缺，已计入 retention=5 名额）。
   - 方案（验收人建议）：复制完成后**原子写 `BACKUP_OK` 标记文件**；列表与 retention 清理只认标记；启动时顺手清理无标记的残缺目录。②即根治，且与「体积猜完整性」脱钩。
   - remove() 的 rmSync 容错（M6 终审遗留 Minor）。
3. **cpSync 阻塞面板事件循环**（备份期一切「状态延迟」的根因：横幅迟到、/api/status 排队、外部观察者难判进度；M6 验收条 7 过程留档实证）：
   若 M7 动备份模块：复制改分片/异步（按文件分批 + `setImmediate` 让路），或至少保证备份期间 `/api/status` 可应答——同时改善条 5 的 tag 滞留与逃生口的可观察性。
4. **健康后端下导航静默中止一次**（低频、可自恢复，全程仅一次）：
   首次点「请求日志」无反应（URL 不变、无自愈键写入、无提示），重试即恢复——与 M6 自愈所修症状同型但无导入失败证据。建议先在 `router.onError` 现有 else 分支补结构化埋点日志观察，拿到发生条件再定修法。
5. **备份页「备份进行中」tag 滞留**（纯 UI）：
   面板死亡时 POST /backups 永不返回，页面 running 态无法复位（刷新即恢复）。若条 3 落地可能自然改善；否则前端对 POST 加超时兜底。

## 验收技巧沉淀（同类竞速场景复用）

外部 watcher 轮询 `/api/status` 触发击杀，比「浏览器见横幅→模型转发→命令行杀」快且稳；PowerShell 冷启动 1~3s，watcher 需先启动预热再触发场景。README M6 清单条 7 的实际语义：「横幅出现后立刻强杀」在 cpSync 阻塞下等于「kill 落在浏览器已见 true 且未再见 false 的窗口内」，两条离线路径（快速/容忍上限）都算通过。
